## Stopped imgproxy candidate: retained original proposal

The candidate is the existing open-source imgproxy image-processing service,
using one fixed local image and one fixed resize-and-encode operation. This
changes the application and computational operation from SHA. imgproxy shares
Go with the original service, so this is not full runtime independence.

Official sources:
- https://github.com/imgproxy/imgproxy
- https://docs.imgproxy.net/latest/configuration/options

Before any inferential collection:

1. Pin an upstream release/commit, dependency versions and build/container digest.
   Pin an input image hash, dimensions, output format, output dimensions and
   encoding quality. Verify decoded output correctness. Use local input to avoid
   introducing an external download service. Record response size and cache
   policy; every measured request must execute the declared image operation.
2. Examine the service's actual queue and execution boundaries. Obtain paired
   per-request queue wait and client completion timings with unique request IDs.
   Check that client completion includes receipt of the full response body.
   Aggregated latency histograms alone cannot reconstruct the paired observations.
3. If instrumentation is needed, make a minimal auditable timing-only patch.
   Qualify event completeness, clock semantics and observer cost against the
   uninstrumented service. Set acceptance bounds before that qualification run.
4. Configure one application worker and qualify effective concurrency, including
   libvips/codec threads. A worker setting alone does not establish the original
   serial execution assumptions. Measure CPU consumption and throttle accounting
   for the whole service cgroup; include child processes if any exist.
5. Retain the original host-control, CPU-affinity and owned-cleanup discipline.
   Candidate resource setting: quota 25 ms per 100 ms, zero configured burst.
   If the candidate cannot support interpretable timing or the required execution
   assumptions, record that limitation and stop this candidate.

The feasibility stage must have written run/time caps before execution. It is
engineering qualification, not evidence confirming the scientific prediction.
Do not try image sizes or operations until one produces a favorable model gap.
Any workload revision requires a documented reason and a new candidate version.

## Historical paired-stage proposal for stopped candidates

The proposal below preceded the NGINX source audit and applied to the stopped
instrumented worker candidates. It is retained as design history and does not
authorize NGINX collection. Its queue domain, capacity calibration and comparators
are not established for NGINX. The active replacement draft is linked above.

Separate qualification, calibration and held-out validation. Freeze the final
protocol and executable bundle before calibration/validation collection. The
protocol may contain deterministic rules that resolve numeric settings from
calibration; seal their resolved values and forecasts before validation.

- Obtain fresh busy-window capacity and four independent low-rate calibration
  cohorts. Derive the paired queue-free response CDF from this application using
  the same declared nonnegative-stage and queue<=100 us rules as V31. Do not
  import the SHA timings or capacity estimate.
- Candidate unseen validation rates: 0.15, 0.30 and 0.50 times fresh measured
  busy-window capacity. Finalize rate representation, calibration-rate separation,
  warmup, measurement duration and minimum offers before collection. Capacity
  fractions do not guarantee the scientific queue/throttle domain.
- Candidate primary deadline: the median of the eligible fresh calibration
  response samples, represented in integer nanoseconds with a fixed order-statistic
  rule. This tests the steep part of the new application's latency distribution.
  Keep literal 10 ms as a separately reported secondary deadline. This is a new
  application-transfer design, not an exact replication of V31's fixed 10 ms test.
- Use six balanced three-rate blocks: ABC, BCA, CAB, ACB, CBA, BAC, giving eighteen
  held-out validation trials. Preserve block-level inference; many requests are
  not eighteen thousand independent experimental replications.
- Freeze the empirical-CDF, periodic-plus-delay and fluid predictions before
  inspecting validation outcomes. Define how fresh capacity calibrates each
  model, so a comparator is not accidentally parameterized for the SHA workload.

Proposed primary accuracy criterion: equal-profile/block mean absolute error
<=3 percentage points at the declared primary deadline. Separately test the
V31 advantage criterion: empirical-CDF improvement over periodic-plus-delay is
positive in every block and its declared block-level 95% t lower bound is >=5
percentage points. These proposed thresholds require a calibration-sample and
measurement precision justification in the final protocol. Eighteen trials are
a candidate balanced design, not an established power calculation.

Carry forward the scientific domain: zero recorded measurement throttled periods
and >=99% of all offers with observed queue<=100 us. Count failures and drops in
all-offer outcomes, retain domain exits, and never replace a trial because its
scientific result is unfavorable. Define technical retry limits in advance.

Do not make a near-5% admission claim from a median-deadline experiment. Any
decision endpoint near that threshold needs its own predeclared calibration rule,
sufficient tail samples and uncertainty treatment.

## Interpreting the outcome

- Accuracy and comparator-advantage gates pass inside the domain: the specific
  V31 pattern transfers to this second application on this host.
- Accuracy passes but advantage does not: the calibrated CDF transfers, but the
  original comparator failure does not transfer under these conditions.
- Accuracy fails inside the domain: retain a counterexample limiting the claim.
- Domain or technical qualification fails: report an applicability or measurement
  limitation; do not call it confirmation or quietly discard it.

Even a positive result would support two tested applications on one host. Hardware
generality and independent-team replication remain open. Release a self-contained
protocol, pinned inputs/builds, raw records and analysis instructions so another
group can later test those dimensions without help from the original team.
